ffcheat real-data decode
========================

Where this ran
--------------
BlueStacks 5, Android 9 (API 28), x86_64.
The test binary was built for x86_64 and ran natively - no ARM translation was
involved, so what is being measured is the decoder and not libhoudini.

Input
-----
  global-metadata.dat   56,970,552 B   from split_asset_pack_install_time.apk
  libil2cpp.so         184,044,016 B   from split_config.arm64_v8a.apk,
                                       with .rela.dyn applied by sofix.py
  total mapped         241,014,568 B   over 9 PT_LOAD segments

The point of the test
---------------------
Two independent readers of the same two files. The Python dumper
(tools/ffdump/ffdump.py) produced the numbers first. The C++ decoder is what
ships inside the cheat. They agree on everything, or something is wrong in one
of them.

What it proves
--------------
  the metadata header is found by its sanity value and version, from a scan
  the type table decodes to 43,627 entries
  Il2CppMetadataRegistration is reached by RVA and yields the field-offset
    pointer 0xa8bf168, the same value the Python reader found
  COW.GamePlay.Player is found at type 31821 with 1,689 fields and 4,136 methods
  all seven field offsets the ESP depends on match the generated header exactly

What it does not prove
----------------------
  the live class scan        there is no IL2CPP runtime in this process, so there
                             is no Il2CppClass to find. The scan correctly
                             reports no hit; it cannot be exercised further
                             without a running game.
  the player list            not implemented, and not findable statically
  drawing                    needs a live camera matrix
  that Free Fire boots in the container   a separate question, and the one that
                             still needs a real phone

Three bugs this test found, all of which looked fine
----------------------------------------------------
  Range::contains accepted any address above a range's start, because
  `end - addr` underflows and every size is smaller than a wrapped value. One
  region masked it; two regions made it a segfault.

  MappedMemory::read had its own copy of that same test, so fixing the shared
  one changed nothing for the path that was failing.

  add_elf read e_phnum at 0x3A, which is e_shentsize. Program headers and
  section headers are different tables two bytes apart.

None of the three produced a wrong-looking number in a small test. The first two
needed two mapped regions to appear at all, and the third needed an ELF whose
file offsets differ from its virtual addresses - which is every real shared
object, and no fixture until this one.
